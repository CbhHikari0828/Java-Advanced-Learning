# chapter02_synchronization 学习笔记

## 竞态条件的理解

多个线程同时执行 `counter++` 会丢失更新，因为 `counter++` 不是一个不可拆分的动作，它大致包含“读取 counter、加 1、写回 counter”三步。

如果两个线程同时读到同一个旧值，例如都读到 `123`，它们各自加 1 后都会写回 `124`，最终就会缺失一次加一。

## synchronized 的理解

`synchronized` 不是把共享变量变成某个线程私有，而是保护修改共享变量的临界区，让同一时间只有一个线程能执行这段代码。

在当前 Demo 中，临界区是：

```java
counter++;
```

把它放进 `synchronized` 方法后，两个线程会一个一个进入 `increment()`，从而让最终结果稳定回到理论值。

## 锁对象的理解

`synchronized` 代码块括号里写谁，就使用谁作为锁对象；大括号里写的代码，才是这把锁保护的临界区。

只有竞争同一把锁的线程，才会互相等待。不同线程如果使用不同锁对象，即使代码里都有 `synchronized`，也不会互相阻塞。

实例同步方法锁的是当前对象 `this`：

```java
public synchronized void instanceMethod() {
    // 等价于 synchronized (this)
}
```

静态同步方法锁的是当前类的 `Class` 对象：

```java
public static synchronized void staticMethod() {
    // 等价于 synchronized (当前类.class)
}
```

所以，同一个对象调用 `synchronized` 实例方法会排队；不同对象调用实例同步方法不会互相阻塞；实例同步方法和静态同步方法也不会互相阻塞，因为它们使用的不是同一把锁。

## synchronized 可重入的理解

`synchronized` 是可重入的：同一个线程已经持有某把锁时，可以再次进入由同一把锁保护的代码。

例如：

```java
public synchronized void outer() {
    inner();
}

public synchronized void inner() {
}
```

`outer()` 和 `inner()` 锁的都是当前对象 `this`。当同一个线程进入 `outer()` 后，它已经持有 `this` 这把锁；随后在 `outer()` 内部调用 `inner()` 时，可以再次获得同一把锁并继续执行。

如果 `synchronized` 不可重入，线程在 `outer()` 内调用 `inner()` 时就会自己等待自己释放锁，从而卡住。

## volatile 的理解

`volatile` 保证可见性：一个线程修改变量后，其他线程能及时看到这个修改。

例如一个线程在 `while (running)` 中循环，另一个线程把 `running` 改成 `false`。如果 `running` 没有使用 `volatile`，循环线程可能一直看不到变化；加上 `volatile` 后，循环线程可以看到变化并退出。

`volatile` 不保证原子性：`counter++` 这种“读 counter、加 1、写回 counter”的复合操作仍然可能丢失更新。

所以：

```text
volatile：保证变量修改对其他线程可见，但不保证一组操作不可打断。
synchronized：保护临界区，让同一时间只有一个线程执行这段代码。
```

## wait / notify 的理解

`wait / notify` 解决的是线程协作问题：一个线程在条件不满足时等待，另一个线程把条件准备好后通知它继续执行。

`wait()` 必须在 `synchronized` 中调用。线程调用 `LOCK.wait()` 后，会释放 `LOCK`，进入 `WAITING` 状态，并进入 `LOCK` 这个对象的等待队列。

`notify()` / `notifyAll()` 也必须在 `synchronized` 中调用。`LOCK.notify()` 唤醒的是在 `LOCK.wait()` 上等待的某一个线程。

被唤醒的线程不会立刻继续执行，它还要重新竞争 `LOCK`；等重新拿到锁后，才会从 `wait()` 后面继续执行。

标准等待写法要使用 `while`，而不是 `if`：

```java
while (!ready) {
    LOCK.wait();
}
```

原因是线程被唤醒后，不代表条件一定满足。可能出现虚假唤醒，也可能多个等待线程被唤醒后竞争同一个条件，所以醒来后必须重新检查条件。

`notify()` 只唤醒一个等待线程；`notifyAll()` 会唤醒所有等待线程，让它们重新竞争锁并检查条件。复杂协作场景下，`notifyAll()` 通常比 `notify()` 更稳妥。
