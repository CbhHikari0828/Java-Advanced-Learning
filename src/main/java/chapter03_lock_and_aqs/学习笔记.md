# chapter03_lock_and_aqs 学习笔记

## ReentrantLock 的理解

`ReentrantLock` 是 `java.util.concurrent.locks` 包里的显式锁，用来保护临界区，避免多个线程同时修改共享变量。

它和 `synchronized` 的共同点是：同一时间只允许一个线程进入被锁保护的代码。

区别在于：

```text
synchronized：由 JVM 自动加锁、自动释放锁。
ReentrantLock：需要手动 lock()，也必须手动 unlock()。
```

所以使用 `ReentrantLock` 时，最标准的写法是：

```java
LOCK.lock();
try {
    // 临界区
} finally {
    LOCK.unlock();
}
```

## try/finally 与 unlock

`ReentrantLock` 不会因为代码块结束就自动释放锁。

如果只调用 `lock()`，但没有调用 `unlock()`，其他线程会一直等待这把锁，程序可能卡住。

把 `unlock()` 放进 `finally` 的原因是：即使 `try` 中的代码抛出异常，`finally` 也会执行，从而保证锁被释放。

这个实验说明了：

```text
try 里面出错，不代表锁会自动释放；真正保证释放的是 finally。
```

## 可重入的理解

`ReentrantLock` 的 `Reentrant` 表示“可重入”。

可重入的意思是：同一个线程已经持有某把锁时，可以再次获取同一把锁。

例如：

```text
outer() 拿到 LOCK
outer() 调用 inner()
inner() 再次拿同一把 LOCK
```

如果锁不可重入，线程会自己等自己释放锁，程序就会卡住。

`ReentrantLock` 内部会记录重入次数：

```text
第一次 lock()：state = 1
第二次 lock()：state = 2
第一次 unlock()：state = 1
第二次 unlock()：state = 0，锁真正释放
```

所以：

```text
同一个线程 lock 几次，就必须 unlock 几次。
```

## tryLock 的理解

普通的 `lock()` 是：

```text
拿不到锁就一直等。
```

`tryLock()` 是：

```text
尝试获取锁，拿到返回 true，拿不到立刻返回 false。
```

因此 `tryLock()` 适合“不想一直等锁”的场景：

```text
拿到锁就执行临界区；
拿不到锁就放弃本次操作，或者执行备用逻辑。
```

在 `TryLockDemo` 中，有些线程没有拿到锁，所以对应的累加不会发生，最终计数值可能小于总尝试次数。

## tryLock(timeout) 的理解

`tryLock(timeout, unit)` 介于 `lock()` 和 `tryLock()` 之间：

```text
lock()：一直等。
tryLock()：不等，拿不到立刻放弃。
tryLock(timeout)：最多等一段时间，等不到再放弃。
```

使用定时 `tryLock` 时，要特别注意：

```java
boolean locked = false;

try {
    locked = LOCK.tryLock(200, TimeUnit.MILLISECONDS);
    if (locked) {
        // 临界区
    }
} finally {
    if (locked) {
        LOCK.unlock();
    }
}
```

只有真正拿到锁时，才能调用 `unlock()`。

如果线程没有拿到锁却调用 `unlock()`，会抛出 `IllegalMonitorStateException`。

## Condition 的理解

`Condition` 是 `ReentrantLock` 体系下的线程协作机制，可以理解为 `wait / notify` 的显式锁版本。

对应关系大致是：

```text
synchronized        -> ReentrantLock
wait()              -> condition.await()
notify()            -> condition.signal()
notifyAll()         -> condition.signalAll()
```

`Condition` 依附于某一把 `ReentrantLock`：

```java
private static final ReentrantLock LOCK = new ReentrantLock();
private static final Condition CONDITION = LOCK.newCondition();
```

调用 `await()`、`signal()`、`signalAll()` 时，都必须先持有对应的锁。

`await()` 的核心动作是：

```text
释放锁 + 进入 Condition 等待队列。
```

等待线程被 `signal()` 或 `signalAll()` 唤醒后，不会立刻继续执行，而是要重新竞争锁。只有重新拿到锁以后，才会从 `await()` 后面继续执行。

`await()` 外面要使用 `while`，不要使用 `if`：

```java
while (!ready) {
    CONDITION.await();
}
```

原因是：线程被唤醒并不代表条件一定成立。可能出现虚假唤醒，也可能在重新抢到锁之前，条件已经被其他线程改变。

## signal 与 signalAll

`signal()` 唤醒当前 `Condition` 等待队列中的一个线程。

`signalAll()` 唤醒当前 `Condition` 等待队列中的所有线程。

它们都不是让线程立刻运行，而是让等待线程有资格离开 `Condition` 等待队列，重新参与锁竞争。

简单对比：

```text
signal()：叫醒一个，性能更好，但要确保叫醒一个就够。
signalAll()：叫醒全部，更稳妥，但会带来更多线程竞争。
```

## AQS 的初步理解

AQS 全名是 `AbstractQueuedSynchronizer`，是 Java 并发包里用来构建锁和同步器的基础框架。

可以先粗略理解为：

```text
AQS = 一个状态变量 + 一个等待队列
```

在 `ReentrantLock` 里：

```text
state = 0：锁空闲。
state > 0：锁已被某个线程持有，也可以表示重入次数。
```

拿不到锁的线程不会一直空转消耗 CPU，而是会进入 AQS 的同步队列，并被挂起等待唤醒。

简化后的 `lock()` 流程：

```text
如果 state == 0，当前线程拿到锁。
如果 owner 是当前线程，说明是可重入，state + 1。
如果锁被其他线程持有，当前线程进入等待队列。
```

简化后的 `unlock()` 流程：

```text
如果当前线程不是持锁线程，抛出 IllegalMonitorStateException。
state - 1。
如果 state 变成 0，锁真正释放，并唤醒等待队列中的后继线程。
```

`Condition` 和 AQS 的关系可以这样理解：

```text
AQS 同步队列：存放抢锁失败、等待获取锁的线程。
Condition 等待队列：存放调用 await()、等待条件满足的线程。
```

`signal()` 会把线程从 `Condition` 等待队列转移到 AQS 同步队列，让它重新参与抢锁。

## 公平锁和非公平锁

`ReentrantLock` 默认是非公平锁：

```java
new ReentrantLock()
new ReentrantLock(false)
```

也可以显式创建公平锁：

```java
new ReentrantLock(true)
```

区别是：

```text
非公平锁：锁空了就先抢，可能插队，吞吐量通常更好。
公平锁：先看前面有没有线程排队，尽量按顺序来，等待更公平但性能通常更低。
```

`synchronized` 不提供公平性选择，也不保证等待最久的线程一定先拿到锁。

## synchronized 和 ReentrantLock 的区别

```text
synchronized：
- JVM 语法级锁
- 自动加锁、自动释放
- 可重入
- 不支持手动公平性
- 不支持 tryLock
- 不支持多个等待条件队列

ReentrantLock：
- JUC 包里的显式锁
- 手动 lock / unlock
- 可重入
- 支持 tryLock
- 支持 tryLock(timeout)
- 支持公平锁 / 非公平锁
- 支持多个 Condition
```

一句话总结：

```text
synchronized 简单、自动；ReentrantLock 手动、灵活；AQS 是 ReentrantLock 背后管理状态和队列的底层框架。
```
